# Solo Supper

Dinners for one, planned a week out. Over four hundred single-portion recipes, a weekly planner, and a shopping list that adds itself up and scales to how many people you are cooking for.

The site has two halves:

- **The public site** (home page, every recipe as its own page, collections and cuisines). These are plain static HTML pages generated from the recipe data, so search engines can read them.
- **The planner** in `plan/`, the app itself. Sign in with Google is optional: without it everything is saved to the browser you are using; with it, your week, servings and shopping list sync across devices.

## Files

- `recipes-data.js`: every built-in recipe. Edit recipes here; both the planner and the page generator read it.
- `plan/index.html`, `app.js`, `styles.css`: the planner.
- `firebase-config.js`: your Firebase project's settings (sign-in and sync).
- `scripts/build-site.js`: builds the public pages from `recipes-data.js`.
- `assets/site.css`, `assets/site.js`, `favicon.svg`: styling and small scripts for the public pages.
- Generated by the build (do not edit by hand): `index.html`, `recipes/`, `collections/`, `cuisines/`, `404.html`, `sitemap.xml`, `robots.txt`.
- `img/recipes/<id>.webp`: photos of each finished dish.
- `admin.html`: the private business dashboard. Its numbers are stored privately in Firestore (`admin/dashboard`) and only admins can read them.

## Rebuilding the public pages

Whenever recipes or photos change, run this from the repo folder:

```
node scripts/build-site.js
```

It needs Node 16 or newer and nothing else. It rewrites the generated pages and the sitemap. Commit the results along with your change.

The live address used for canonical links, the sitemap and social previews comes from `SITE_URL`. It defaults to the GitHub Pages address; once the site has its own domain, build with:

```
SITE_URL=https://your-domain.com node scripts/build-site.js
```

(In PowerShell: `$env:SITE_URL="https://your-domain.com"; node scripts/build-site.js`)

### Hosting on Cloudflare Pages

Connect this repository in Cloudflare (Workers & Pages, Create, Pages, Connect to Git), production branch as set on GitHub, then:

- Build command: `node scripts/build-site.js`
- Build output directory: `/`
- Environment variable: `SITE_URL` set to your domain, e.g. `https://your-domain.com`

Every push then rebuilds and deploys. Add the new domain to Firebase under Authentication, Settings, Authorized domains so sign-in keeps working.

### Android app

The Android build (solo-supper-android) copies the planner from `plan/index.html` with its `sync-web-assets.sh` script. The public pages are not part of the app.

## 1. Try it with no setup

Serve the folder with any static web server (for example `python -m http.server`) and open `/plan/`. Everything works, saved to that browser's local storage only. Do the Firebase setup below only when you want Google sign-in and cross-device sync.

## 2. Publish on GitHub Pages

1. Create a new GitHub repository (public or private both work with Pages).
2. Add the files to it and push.
3. In the repository, go to **Settings > Pages**.
4. Under **Build and deployment**, set **Source** to "Deploy from a branch", branch `main`, folder `/ (root)`.
5. Save. GitHub gives you a URL, usually `https://<your-username>.github.io/<repo-name>/`. It can take a minute or two to go live the first time.

## 3. Set up Google sign-in and sync (optional)

This uses Firebase, Google's free backend for exactly this kind of thing (auth plus a small database). The free tier is far more than this app needs.

### Create the Firebase project

1. Go to the [Firebase console](https://console.firebase.google.com/) and click **Add project**. Name it anything (e.g. "plate-and-list") and finish the wizard (you can leave Google Analytics off).
2. In the project, click the **web** icon (`</>`) to register a web app. Give it a nickname; you don't need Firebase Hosting.
3. Firebase shows you a `firebaseConfig` object. Copy the values into `firebase-config.js` in this project, replacing the `YOUR_...` placeholders. This config is not a secret and is fine to commit to a public repo; it just points the app at your project.

### Turn on Google sign-in

1. In the Firebase console, go to **Build > Authentication**.
2. Click **Get started**, then open the **Sign-in method** tab.
3. Click **Google**, toggle it **Enable**, pick a support email, and **Save**.

### Create the database

1. Go to **Build > Firestore Database** and click **Create database**.
2. Choose a location close to you and start in **production mode** (the security rules below lock it down properly).

### Set security rules

Each signed-in user should only be able to read or write their own data. In the Firestore console, open the **Rules** tab and replace the contents with:

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{userId}/planner/{docId} {
      allow read, write: if request.auth != null && request.auth.uid == userId;
    }
    // Who has Pro: readable by its owner, written only by the server.
    match /entitlements/{userId} {
      allow read: if request.auth != null && request.auth.uid == userId;
    }
    // giftCodes and stripeCustomers: no client access at all.
  }
}
```

Click **Publish**. This is what actually protects your data; the config file being public is fine because of this rule.

### Allow your GitHub Pages domain to sign in

1. In **Authentication > Settings > Authorized domains**, click **Add domain**.
2. Add your GitHub Pages domain, e.g. `<your-username>.github.io`.
3. `localhost` is already allowed by default, so sign-in works while testing locally too.

### Done

Push the updated `firebase-config.js` to your repository (GitHub Pages picks it up automatically on the next deploy). Open the site, click **Sign in with Google**, and your plan will start syncing. Sign into the same Google account on another device and it appears there too.

## About the "secrets detected" email from GitHub

GitHub's scanner flags any string shaped like a Google API key, including this one, but a Firebase web config key isn't a secret in the way a password or a server-side key is: it just tells the SDK which project to talk to, and it's designed to sit in public client-side code. Real protection comes from the Firestore rules above (only a signed-in user can touch their own data) and, optionally, restricting what the key itself can be used for. Worth doing both:

1. In the [Google Cloud Console](https://console.cloud.google.com/apis/credentials) (same project), find this API key under **Credentials**, open it, and under **Application restrictions** choose **Websites** and add:
   - your GitHub Pages domain, e.g. `your-username.github.io/*`
   - `localhost` for local testing
   - **your Firebase auth domain itself**: `your-project-id.firebaseapp.com/*`

   That last one is easy to miss and breaks Google sign-in if it's left out: the sign-in popup loads a handler page hosted on `<project-id>.firebaseapp.com`, and that page is what actually calls the API with this key, not the page the user started on. Without it allow-listed, sign-in fails with "The requested action is invalid." If you hit that error after restricting the key, this is almost always why; add the auth domain and it clears up immediately (existing open tabs may need a refresh).
2. Under **API restrictions**, limit it to just the APIs this app uses (Identity Toolkit API, Token Service API, Cloud Firestore API, Firebase Installations API) rather than leaving it unrestricted.
3. Back on the GitHub alert, once you're happy with the above, you can dismiss it (as a false positive, or "won't fix") rather than rotating the key, since a fresh key would carry the same "risk" GitHub is flagging.

## How the sync works

- Everything is saved to the browser's local storage immediately, on every change, whether or not you're signed in. This means the app is fully usable offline or without ever setting up Firebase.
- When signed in, changes are also written to Firestore (in a document scoped to your account, under a short delay so rapid changes like ticking off shopping items don't spam the network) and a live listener keeps every open tab or device in sync automatically, no refresh needed.
- Signing out just stops the cloud sync; what's already on the device stays there.


## Pro, payments and gift codes

The website is free; **Pro** adds low-waste planning, planning next week and your own recipes. New accounts get a 14-day trial with no card. Payments go through **Stripe Managed Payments** (Link is the merchant of record, so it handles VAT, receipts and disputes).

The small server lives in `functions/` and runs as **Cloudflare Pages Functions** at `/api/*` (`_routes.json` keeps every other page static, so they don't count towards the Functions limit). No Firebase Blaze plan is needed.

| Path | What it does |
| --- | --- |
| `GET /api/health` | Shows which settings are in place (never the secrets) |
| `POST /api/account` | Starts the trial on first sign-in, returns Pro status |
| `POST /api/checkout` | Opens Stripe Checkout for the yearly or monthly price |
| `POST /api/portal` | Opens Stripe's customer portal (manage or cancel) |
| `POST /api/redeem` | Applies a gift code |
| `POST /api/delete-account` | Deletes the account, its data and any subscription |
| `POST /api/admin` | Admin page: make gift codes, give or remove free Pro |
| `POST /api/stripe-webhook` | Stripe reports subscription changes here |

Who has Pro is stored in Firestore at `entitlements/{uid}`, written only by these functions.

### Settings in Cloudflare (Pages project > Settings > Variables and secrets)

| Name | Value |
| --- | --- |
| `FIREBASE_SERVICE_ACCOUNT` | The whole JSON key from Firebase > Project settings > Service accounts > Generate new private key (secret) |
| `STRIPE_SECRET_KEY` | `sk_test_...` while testing, `sk_live_...` when live (secret) |
| `STRIPE_WEBHOOK_SECRET` | `whsec_...` from the webhook endpoint in Stripe (secret) |
| `STRIPE_PRICE_ANNUAL`, `STRIPE_PRICE_MONTHLY` | Only needed for live mode; the test price IDs are built in |
| `ADMIN_EMAILS` | Optional; defaults to neil.fletcher@gmail.com |

After changing them, redeploy (Deployments > ... > Retry deployment) and check `https://solosupper.co.uk/api/health`.

### Stripe

- Webhook endpoint: `https://solosupper.co.uk/api/stripe-webhook` with the events `checkout.session.completed`, `customer.subscription.created`, `customer.subscription.updated` and `customer.subscription.deleted`.
- Settings > Tax: turn on **Include tax in prices**, so £14.99 means £14.99.
- Settings > Billing > Customer portal: turn it on, allowing cancelling and switching between the two prices.
- Settings > Checkout: add the terms (`/terms/`) and privacy (`/privacy/`) links. Business details: support email hello@solosupper.co.uk, statement descriptor SOLOSUPPER.

### Firebase

- Authentication > Sign-in method: turn on **Email/Password** and, inside it, **Email link (passwordless sign-in)**.

## Keeping it running

- **Uptime.** `.github/workflows/uptime.yml` checks the home page, a recipe page, the planner, the recipe data and `/api/health` (Firebase and Stripe settings) every 15 minutes. When something breaks, that run fails and GitHub emails you; while it stays broken you get a reminder every 6 hours rather than an email every 15 minutes.
- **Errors in people's browsers.** `assets/telemetry.js` sends errors from the site's own scripts to `/api/log`, stored in Firestore under `clientErrors` (one document per distinct error, with a count). They show on the admin page under "Is anything broken", where you can clear them once fixed.
- **Where customers come from.** For people who allow usage statistics, `assets/telemetry.js` remembers how they first arrived (utm_source, or the referring site) and the page they landed on, and `/api/account` saves it with their account as `ftSource`, `ftCampaign`, `ftLanding`. The admin page shows sign-ups and payments by source. Tag your own links with `?utm_source=...&utm_campaign=...` to tell them apart.
- **Backups.** `.github/workflows/backup.yml` runs `scripts/backup-firestore.js` every night: every Firestore document and the list of sign-in accounts, encrypted with the `BACKUP_PASSPHRASE` GitHub secret and kept as a workflow artifact for 30 days (Actions > Nightly backup > a run > Artifacts). To open one: `BACKUP_PASSPHRASE=... node scripts/backup-decrypt.js solo-supper-YYYY-MM-DD.ssbk > backup.json`. Keep the passphrase in your password manager; without it the backups can't be read.

## The cookbook PDFs

Sold on `/books/` and included with Pro (yearly: all four, monthly: Asia, once the first payment has gone through). Code: `functions/_shared/books.js`, the `book-*` routes in `functions/api/[[route]].js`, `assets/books.js`, and "Your books" in the planner's settings.

Setup, once:
1. **Files.** Cloudflare > R2 > Create bucket `solo-supper-books` (private). Upload the four screen PDFs, named exactly `solo-supper-asia.pdf`, `solo-supper-mediterranean-middle-east.pdf`, `solo-supper-americas-africa.pdf`, `solo-supper-britain-europe.pdf`.
2. **Binding.** Workers & Pages > solo-supper > Settings > Bindings > Add > R2 bucket: variable name `BOOKS`, bucket `solo-supper-books`. Redeploy.
3. **Prices.** In Stripe, create five one-off products (tax category: e-books / digital books), and put each price ID in Cloudflare variables: `STRIPE_PRICE_BOOK_ASIA`, `STRIPE_PRICE_BOOK_MED`, `STRIPE_PRICE_BOOK_AMERICAS`, `STRIPE_PRICE_BOOK_BRITAIN`, `STRIPE_PRICE_BOOK_ALL`. The prices shown on the page are `BOOK_PDF_PRICE` and `BOOK_BUNDLE_PRICE` in `scripts/build-site.js`; keep them the same.
4. **Amazon links.** Add each book's paperback and kindle links to `BOOK_LIST` in `scripts/build-site.js` (until then the button searches Amazon for the title).

`/api/health` shows `books.bucket` and how many prices are set. Purchases are recorded in Firestore under `purchases/{checkout session}`; a buyer who later signs in with the same email sees the books in their account.
